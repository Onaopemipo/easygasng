# EasyRewards workflows

1. Owner/finance proposes versioned loyalty.policy in existing Business Settings; separate owner and finance approve. Business approval and technical activation are separate gates. No live policy/flag was activated here.
2. Delivered + verified paid order records one award job. Unverified COD, placement, cancellation and failed delivery award nothing. Existing driver/custody/capacity/proof and independent cash-verification controls remain in force. Worker retries calculation from frozen policy/line evidence and posts one earned entry.
3. Customer /rewards displays the authoritative balance, recent history, actual pending event count, approved rules and unavailable states. Product, gas and combined checkout reuse RewardCheckoutField; native product checkout uses the additive wallet rewardsInfo response. Optional rewardPoints goes through the existing checkout. Minimum/cap/ownership/stock/price/location/payment are revalidated on the server. Fees remain unchanged. Point debit, order and discount are one transaction, so an abandoned failed transaction has no leaked hold.
4. Cancellation before fulfilment restores the exact debit. Delivered verified full refund uses existing refund.request / credit.decide independent finance flow, refunds the reduced monetary total, reverses original earned/referral awards and restores the checkout discount once. Partial refund/fulfilment allocation remains NOT_IMPLEMENTED and must not be enabled through an ad hoc amount parameter.
5. Under approved referral policy, customers generate a stable opaque code in /rewards. Share link uses HTTPS configured APP_URL only. Registration attempts attribution from ref= after auth succeeds; failure is reported without undoing account creation. Existing customers may enter a code before a qualifying purchase. One referrer/customer, no self-referral, active same-branch identities, first verified fulfilled purchase only. Public history hides the referred customer's/order identity. Refund reverses the original bonus.
6. Business Settings loyalty.adjustment uses existing independent owner+finance approval; branch/active customer checked on activation, reason and evidence immutable. Negative point state is restricted and enters finance review, never an automatic monetary debit.
7. Existing admin Campaigns contains reconciliation; existing Business Settings and Approval Centre own policy/correction requests. Scoped export reauthenticates on the server and audits the export. No additional admin route/sidebar is created. Catalogue moderation, campaign budgets and a dedicated suspicious-referral review interface remain outstanding.

Smart Refill: current schedules/recurring/refill notifications are preserved. No offer or campaign earns on a schedule, fabricated usage, preferred date or notification. Optional point promotion integration remains blocked until core acceptance and real approved offers/consent/budgets exist.

## Completed application paths

- /orders exposes selected-quantity refunds alongside the existing full remaining refund. Native orders expose the same API and explicit purchase-credit request. Backend owns all prices, remaining units and discount/point allocation; no arbitrary refund amount is accepted.
- Business Settings includes a typed catalogue/budget/service policy editor and referral review editor. Existing Campaigns shows offer budget consumption, referral review identifiers/evidence and posting review retry controls. No sidebar route was added.
- Customer /rewards shows approved eligible offers, progress to minimum, actual history and referral sharing/attribution. Product, gas and mixed checkout carry offer identity and point choice through the existing checkout. Native product/gas/mixed checkout use one reusable selector; native rewards/referrals and consented Smart Refill offers use the same backend.
- Existing refill profiles show only offers matching actual verified forecast history and consent. Maintenance may create deduplicated in-app notices outside quiet hours; no automatic promotional point award, new recurring charge or fabricated usage is created.

Partial physical delivery remains prohibited by the existing all-items handover/manifest safety controls. This continuation adds financial line refunds; it does not claim a qualified partial-cylinder handover process exists.
