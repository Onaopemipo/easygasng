# Staff privilege audit and implementation scope

The existing staff UI uses staff.manage and staff.access.request; security.permissions governs role and branch replacement only. Actor authentication reloads the current user on every dispatch. allow() applies role and optional branch constraints. Administration navigation derives from existing grouped route definitions, and dedicated driver/technician session boundaries and governance qualification/approval checks are separate. No per-user privilege storage exists.

Extend these components with a server-defined capability catalogue and per-user grant/deny/default overrides; retain canonical identities, roles, financial histories and existing routes. A grant is scoped to named operations, never impersonates a role, never changes global scope and never substitutes a qualification or independent approval. Protected authority can be restricted but requires the existing role to exercise it. Owner and technical administrator may manage overrides, with fresh identity verification, stale-version checks, audit records and no self-edit or delegated privilege administration. Field/customer identities keep their existing access boundaries; staff eligibility is required for additional business grants.

Acceptance requirements: STAFF-PRIV01 individual default/grant/deny controls and truthful effective access; STAFF-PRIV02 backend enforcement, current-session revocation and branch/identity protections; STAFF-PRIV03 usable Staff Management integration and retained role workflow. Prior production NO-GO and other phase work remain unchanged. This phase does not change actual demo user privileges during visual checks.
