# Customer dashboard security

Server-side auth.actor validates the existing HttpOnly sameSite=lax cookie against active users and unexpired, unrevoked sessions. Secure cookie is set in production; local HTTP does not pretend to provide production TLS. The existing POST origin/content-type/body limits, verification requirements and private database policy remain unchanged. No tokens are stored in browser local/session storage or passed into UI preference state.

Protected pages validate the session before rendering. API dispatch independently authenticates each request. New customer.dashboard reads permit customer/commercial roles, reject extra fields/customer IDs and bind every query to actor.id. Orders/activity/history/default address/notification counters cannot use a browser-supplied identity. Existing wallet, rewards, schedules, profiles, bookings, support, addresses and notification mutations retain their ownership predicates. Browser hints/preferences never grant privileges.

Wallet/reward cards read the authoritative signed ledger including adjustments/reversals. No unverified top-up is represented as balance; online top-up is explicitly unavailable. Purchase history requires delivered status, verified payment status, payment evidence and delivery timestamp provenance. Estimates remain purchase-based and confidence-labelled. External-refill or sensor measurements are not invented.

Identity changes unmount customer data resources; requests abort and event/timer handlers clean up. Session revalidation covers visibility/focus/pageshow/route/30-second checks. A 401 clears customer state and protected pages return to safe login. Logout invalidates the backend session, clears private session drafts and navigates the document; a timestamp-only cross-tab event triggers revalidation/clearing elsewhere. No private data cache was introduced. Source failure clears its card; navigation failure hides unavailable indicators.

Negative automated tests cover tampered customer IDs, other-user notifications/addresses, role denial, absent/revoked/expired sessions and verified-history exclusions. Existing service/account/security suites also ran. Browser cross-tab logout showed zero protected dashboard headings; customer B showed only its empty account after customer A. This local evidence does not certify managed multi-connection RLS, penetration resistance, email delivery or production readiness. Existing NO-GO and blocker register remain in force.

Migration032 only broadens the consumption_feedback state constraint; existing row policies/grants and append-only trigger are unchanged. All five feedback states retain owned active-profile lookup under a row lock and the existing one-hour rate limit. Self-reports/snoozes mark only the same customer/profile’s obsolete estimated reminders read. Verified history is never created by feedback; a later verified purchase supersedes self-report suppression. Worker integration and exact 24-hour boundaries are tested. A hosted Supabase advisor/managed RLS run is not available in this local PGlite-only phase; no hosted migration was applied.
