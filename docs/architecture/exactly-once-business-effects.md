# Exactly-once committed business effects

This is an application/database boundary, not exactly-once network delivery. A logical operation supplied with operationKey is wrapped around the existing professionalServiceAction inside dispatch's authoritative transaction. It is identified by a UUID, actor, action and canonical payload hash. Unique operation_key prevents competing executions. INSERT ON CONFLICT followed by SELECT FOR UPDATE waits for the winner. Same identity/request returns the stored result; different body/actor/action/role/branch conflicts.

The pending result row is uncommitted. Booking/capacity changes, financial/material changes, events, in-app notifications, email outbox and committed result either commit together or roll back together. Only COMMITTED rows persist in ordinary operation; there is no separate HTTP processing worker or lease to become stale. Uncertain HTTP/COMMIT outcomes are reconciled by a fresh read/retry using the same key. Result records have no automatic expiry and cannot be changed or deleted after commitment.

Public HTTP booking/material mutations now require an explicit UUID operationKey; HTTP cancellation/rescheduling also require a positive booking version. Requests without these are rejected rather than silently bypassing the result store. Existing internal/trusted callers without operationKey continue to use established natural protections: unique customer/idempotency booking reference, slot/technician locks, versioned rescheduling, one quote decision, unique material/reference and immutable ledger entries. They do not receive the full generic recoverable-result contract. Web booking and service-material forms now submit operationKey. External clients must adopt this contract before using those mutation endpoints. Mixed checkout retains its separate existing authoritative checkout/idempotency boundary. This phase does not claim a universal guarantee for unconverted external clients or every application module.

Capacity is the active service_bookings allocation itself, not a new parallel reservation table. Existing slot/technician row locks and overlap checks serialize conflicting schedules. Migration 033 adds active slot uniqueness; cross-slot interval overlap still depends on the trusted scheduling handler. Multi-connection PostgreSQL acceptance is blocked until its harness runs.

Internal in-app notifications and one logical service-event email outbox entry commit with the booking. Outbox key is service-event:<immutable event id>. Consent and Lagos quiet hours are checked when queued. No external provider or delivery worker is enabled here. A future sender must revalidate preferences and quiet hours, use provider idempotency where supported, lease/retry safely and reconcile lost acknowledgements. Never equate pending with delivered or promise exactly-once email/SMS.

Financial postings and materials retain their existing unique business references and independent approval rules. No online payment connection, direct refund posting, stock correction or ledger rewrite was added. Physical movement still requires custody/receiving checks independently of database uniqueness.
