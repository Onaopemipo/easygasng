# Invoices and payment requests

Current through migration061. Orders and service bookings use the same `customer_invoices` table, number sequence, immutable issued snapshots and independent credit/debit/void notes. Exactly one order or booking source is required. Existing identities, branches, approved service quotation/report records, verified payment/refund ledgers and integer NGN kobo remain authoritative. A draft preview does not create a collectible document or a payment receipt.

Order invoices preserve their issued items, gas, original one-visit fee and discount. Service previews/issues use the current independently approved/customer-approved quotation or immutable fixed-price booking snapshot; successful reports establish actual labour/callout/used-material charges. Corrections never rewrite either the issued invoice or report. Report/invoice mismatches and pending/voided invoice corrections hold chargeable work at the backend. Final material reconciliation can produce a separately approved credit and excess balance.

Service refund scope distinguishes reviewed full-service refunds from excess-payment reconciliation. Full-service review and its existing reward reversal remain available, with net prior-refund revalidation; an approved full-service refund holds further collection for finance reconciliation. Explicit excess refunds are capped by the actual completed report and retain rewards for the service kept. Purchase credit is not represented as a provider cash refund.

View/issue/PDF/history/export paths recheck customer ownership and branch/role permissions. Issued records retain forced RLS, restricted private-runtime access and immutable UPDATE/DELETE protection. PDFs use private/no-store headers. Invoice issue locks the original source and repeated/concurrent issue returns one invoice. Payment-review requests require independent financial authority, opaque hashed expiring/revocable fragment tokens, current invoice version/amount and, for services, exact approved quotation/report identity. Sensitive replay URLs are encrypted. A same-price scope revision invalidates a prior service link. Customer sign-in remains required.

Order Paystack checkout remains sandbox-only and subject to its separately governed availability/verification infrastructure. Service invoice checkout is disabled; existing governed booking payment paths remain separate. A browser return, screenshot, cash report, queue entry or review link never establishes verified settlement. Live credentials, actual provider contracts/receipts and production activation are not accepted by this continuation.

See [current implementation and acceptance limits](../production-completion/service-invoices-implementation.md) and [requirements matrix](../traceability/production-end-to-end-rtm.json). Full draft/revision editing scope, all financial/fulfilment exception variants, browser/device/operational acceptance and independent production gates remain open. Existing NO-GO and actual Excel import hold remain. Mobile builds and server deployment are deferred by the user.
