# Gas pricing and delivery release and rollback

The current release recommendation remains **NO-GO**. Local hosting and unconnected online payments remain the authorised configuration. Do not run a hosted migration or provision a paid project without the separate deployment decision.

Before any release, back up and restore-check the database, record the reviewed source manifest, and test migrations on a disposable copy. Existing installations apply application migration 023, managed policy 024 where applicable, then migrations 025 and 027. Fresh installations may use regenerated `database/bootstrap.sql`. Supabase-managed installations have three CLI-generated migration files under `supabase/migrations`. Their private schema and restricted runtime role must be retained. The local development loader applies local upgrades; production requires an explicit migration command. Do not run database commands against a data directory owned by a development server.

Migration 023 imports the supplied per-kg price, flat fee and four named locations, preserves the old fee in governed history where an owner exists, and creates no real gas stock or operational limits. Migration 025 preserves legacy monetary values and classifies fixed gas kg only from explicit original line labels. Old fixed-refill inventory and price data remain historical; they are not automatically converted into measured bulk gas. Review existing open orders and obtain real counted bulk receipts, operational limits, coverage definitions, qualified inspection procedures, legal policies and authorised payment arrangements before enabling orders. Existing scheduled requests whose policy snapshot no longer matches require a new review.

Post-release verification must check current prices, one delivery fee, location selection, quote conflict handling, saved addresses, capacity and stock bounds, cylinder quarantine/inspection, coverage confirmation, delivery-code handling, reconciliation, the maintenance worker and failure notifications. Monitor activation failures, stale requests, reservations and operational-review flags.

Business rollback is a new independently approved setting request linked to the version being reversed; it never rewrites old orders or setting versions. Application rollback must retain schema 027 and the new safeguards until all new orders are reconciled. Do not deploy an older binary that can bypass gram reservations or coverage controls. Database restore is an operator-owned recovery procedure using a verified backup and reconciliation of activity since the backup, not a destructive down migration. Production recovery ownership and multi-connection PostgreSQL acceptance remain launch gates.

Migration 027 adds the confirmed Cylinder Maintenance offering as an inactive, quotation-only draft with an empty checklist. Its commercial configuration, scheduling and qualified safety checklist require the existing independent approvals before bookings open. The managed migration is `20261029203712_cylinder_maintenance_draft.sql`. Existing service configurations are preserved.
