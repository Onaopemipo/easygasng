## Audit and design

The existing service system already has immutable quotation revisions, customer decisions, independent business review, backend work authorisation, material issue/use/return, private evidence, immutable reports, customer acknowledgement, verified booking payments and reviewed purchase-credit refunds. These are retained. Previously, `customer_invoices` could reference only orders. Migration061 extends that same table to a unique booking source, requires exactly one order or booking, preserves the shared invoice number sequence and immutable issued-record trigger, and retains forced RLS/private-runtime grants. There is no second customer, service, payment or invoice ledger.

`serviceInvoiceSource` resolves the current independently approved/customer-approved, unexpired quotation, the booking's approved fixed-price snapshot, or its successful immutable final report. Draft previews are computed and explicitly non-collectible; they are not a persistent draft editor. Finance/owner can issue an immutable invoice using the existing booking lock. Retry/concurrent issue returns the same invoice. Historical issued records remain available even where a later dispute or changed scope requires reconciliation.

## Operating flow

1. Open an existing service booking. Finance/owner can preview the authoritative price and issue its invoice. An unapproved quotation cannot be issued or made collectible. Existing pre-work verified-payment and quotation approvals still apply.
2. The customer views the invoice from the same booking. The customer invoice history and verified account export include owned service invoices. The PDF endpoint rechecks ownership/branch permissions and sends private/no-store headers.
3. Existing `invoice.correction.propose/decide` operations accept exactly one booking/order source. Credit/debit/void notes use the same independent finance/owner decisions, immutable note history and operation receipts. They cannot rewrite the report or issued invoice. Pending/voided/mismatched service invoices block chargeable work at the backend, even if cash was independently verified.
4. Authenticated payment-review requests use encrypted replay receipts and hashed, expiring/revocable fragment tokens. Service requests also bind the exact quotation/report identity: even an equal-price quotation revision invalidates an earlier link. Request creation/view rechecks the current approved scope and amount. Service invoice online checkout stays disabled; existing governed booking payment paths remain available.
5. After materials are used/reconciled and the actual report is submitted, the invoice exposes the exact report-to-invoice difference. Finance proposes the appropriate note and an independent colleague decides it. A quoted unused material can reduce the effective total without rewriting the original snapshot. The final report must match the adjusted total before it is shown as reconciled.
6. The original verified booking ledger determines net payments and excess. Refund scope is explicit: excess-payment reconciliation can return only the actual excess of completed work, while the existing independently reviewed full-service refund path remains available. Existing requests/default clients retain the service-review scope; no working full-refund feature was removed. Approval rechecks net payments, prior approved refunds, booking status and the selected scope/report entitlement, including stale excess requests. A purchase-credit refund does not fabricate a provider refund. A reviewed full refund initially holds the invoice for reconciliation; a separately proposed and independently approved full credit can close it as refunded with zero due while preserving its original report and issued snapshot. Refunding an excess on completed work does not reverse rewards earned for that retained service; a reviewed full-service refund retains its existing reward reversal.

## Other repaired operations

Dispatch capacity now includes spare physical vehicle LPG and reserved doorstep mass in addition to assigned gas obligations. The final backend vehicle check and board use the same additional-custody calculation. Original allocations are not counted twice. Estimates are deliberately conservative until outstanding assignments complete; these are not road-distance, travel-time, proximity or cost predictions. Missing grounded address/routing evidence is not invented.

CRM exposes unsent win-back counts and a scoped cancel action. Cancellation stops only pending/unleased messages, records actor/reason/message IDs and preserves leased/accepted provider evidence. It does not promise recall. An operation retry has one effect. Daily deduplication is checked before allocating another budget unit, and generic queue responses report persisted state rather than labelling cancelled messages newly queued. Channel status aggregates are now branch-scoped for managers/finance; owners retain cross-branch oversight. Existing consent, opt-out, quiet-hour, expiry, stale-purchase suppression and ambiguous-send quarantine remain.
