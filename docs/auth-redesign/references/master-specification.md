## 4. Screen specifications
### AUTH-001 Sign In
- Compact branded hero with original logo, cylinder artwork and “Welcome back.” Keep existing tagline or approved concise supporting copy.
- Sign In/Create Account switch may be a segmented navigation control, not a second auth state machine. Preserve existing route and back behavior.
- Persistent label “Email or phone number”; accept only existing supported identifiers and normalization rules. Use appropriate autofill and keyboard without blocking phone entry. Password field with show/hide, secure entry and password-manager support.
- Place Forgot password? beside password field or immediately below. Primary Sign In button; loading and duplicate-submit protection. Generic invalid-credential message that does not reveal account existence; preserve server rate limiting and safe errors.
- Retain Create Account and “Open an account link” as visible text actions (the latter is required by existing recovery instructions even though omitted from mockup). Preserve existing assisted link and verification handling.
- Apple/Google buttons and divider appear only when existing real provider integration is verified, configured, supported on that platform and permitted by existing policy. Otherwise omit the entire social section. Do not add provider setup, dummy OAuth, or fake success. Preserve any existing supported alternative sign-in methods.
- On server-confirmed authentication route by actual effective role and approved access state. Preserve safe intended destination, pending cart/order/payment link and existing staff workspace routing. Never trust a client role or arbitrary redirect URL.

### AUTH-002 Create Account
- Original logo, compact cylinder artwork and heading “Create your account.”
- Full name, email address, password; preserve any other currently required fields or consent steps discovered by audit. Use persistent accessible labels, correct autocomplete and inline validation. No staff role selector.
- Password visibility toggle and guidance based on actual server policy. Screenshot states at least eight characters; verify current policy. Mockup's letters/numbers/strength checks are not additional mandatory rules unless server already requires them. Indicators reflect typed password, never prechecked.
- Primary Create Account button and compact “Already have an account? Sign in” link. Preserve existing recovery access, terms/privacy links and verification flows where supported. Do not invent consent or silently accept policies.
- On success follow actual verification/session flow; do not claim account verified or signed in until confirmed. Preserve existing duplicate-account privacy behavior and assisted customer identity linking; never merge accounts based on unverified identifiers.

### AUTH-003 Account Recovery
- Back control, original logo, small envelope/lock illustration (approved asset or simple local vector), heading “Account recovery.”
- Email field with persistent label, appropriate keyboard/autofill and “Send Reset Link” CTA. Keep actual email-only recovery contract unless current backend supports other identifiers.
- Preserve existing instructions: open reset link in EasyGas, or choose “Open an account link” on Sign In and paste the link from email. Keep a direct Sign In return action.
- Generic confirmation: “If an account exists for that email, follow the reset instructions sent to you.” Do not disclose whether email exists or promise delivery if provider is unavailable. Preserve sandbox behavior and resend cooldown/rate limits. Show retry and support only through existing supported pathways.

### AUTH-004 Existing account-link and reset completion (supporting states)
- Audit and retain existing deep-link/universal-link/app-link and manual paste entry, password reset completion, expired/invalid/used token states and email verification where implemented. Apply consistent visual style without inventing endpoints.
- Validate links using existing trusted origin/scheme and token handling. Never log tokens, include them in analytics, expose them in error text, or automatically read clipboard. Preserve single-use/expiry rules and existing session invalidation. Do not store reset tokens in ordinary persistent preferences.
- Show new password and confirmation only as required by existing contract. On server-confirmed reset, follow existing sign-in/session policy. No false success or automatic privileged login.

## 5. Interaction, accessibility and animation
Use restrained 180–280ms fades/slide transitions and subtle hero reveal, no forced delay before input. Honor OS reduced motion and web prefers-reduced-motion; avoid animation during keyboard changes. Native uses existing animation/navigation libraries; no new dependency unless justified. Maintain focus, screen-reader labels, error announcements, contrast WCAG AA, visible focus, keyboard submit, accessible password visibility, 44pt iOS/48dp Android touch targets, text scaling and logical tab order. Web dialogs if existing must trap/restore focus and support Escape. Avoid layout shift on loading and validation. Ensure keyboard does not obscure CTA. No sensitive values in screenshots, telemetry or console logs.

## 6. Security and state handling
Keep existing server authority, session persistence, secure storage, CSRF protections, rate limits, password hashing, verification, account lockout, step-up and independent role approval. Do not alter security policy for UX. No raw password persistence, clipboard capture, secret keys in frontend, unrestricted redirects, or client-only access enforcement. Clear password fields on appropriate screen exit; retain non-sensitive form values on recoverable errors. Handle initial session check, loading, invalid input, invalid credentials, offline, timeout, rate limit, server error, provider disabled, verification required, expired link, used link, successful request, successful reset, role pending and session expiry. No offline auth success or optimistic account creation. Preserve existing sandbox/demo notices and prevent real emails/payments in tests. Avoid showing auth UI to an already authenticated user unless existing step-up flow requires it.
