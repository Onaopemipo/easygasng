# Customer quick search for Credits & Refunds

The existing credit form required a copied UUID. Existing customers/customer-management reads exclude finance, while assisted lookup accepts only complete phone/public IDs and has a different role policy. This phase adds a bounded, finance-specific read over the same users/account_addresses/orders records; it does not introduce a customer store or widen unrelated customer administration.

GET credit.customers requires owner/finance,2–100 trimmed query characters and existing per-account120/minute read budget. It returns at most10 active customer/commercial matches by name/email/public ID/exact internal ID/normalised Nigerian phone, including non-archived address phones. Owner sees authorised global records; finance sees its branch or customers with orders in that branch. Passwords, addresses and wallet balances are not returned. Customer/staff roles cannot enumerate financial customers. Direct credit.request now rechecks customer scope as well as current actor role/branch, active identity and reauthentication, closing a forged-customer-ID gap. Existing receipt uniqueness and financial decision controls remain.

A debounced, cancellable search shows explicit match choices; it never auto-selects the first result. Selection displays actual customer identity/contact/branch and binds hidden canonical IDs to the existing credit request. Changing customer/query unmounts the previous credit form and resets draft values. Missing branch blocks the form with guidance. Existing pending credit/refund cards and finance decisions are filtered to the selected customer, with a clear empty state. Clear/change restores the existing complete authorised request list.

This does not introduce staff-created refunds on behalf of a customer: existing order/service ownership, consent, verified-payment, excess/refund allocation and independent finance decision rules remain authoritative. Selecting an account does not credit a wallet or approve a refund. No live/demo financial mutation was submitted during browser checks. Test fixtures alone create pending cash requests and assert both selected and unrelated wallets remain unchanged.
