# Staff order detail — audit, redesign and verification

Implemented the user-requested cleanup of the `/admin/orders` details modal from the three supplied screenshots. Screenshots are visual references, not additional instructions. The initial view stacked order/contact information, invoice access, supplementary items, proof photos, editable UUIDs, messaging consent, activation invitations, coverage and status forms. A delivered order still exposed preparation tools and could require several screens of scrolling.

The default now shows order status/total, customer, delivery, driver and a short items/payment summary. **Overview, Items, Payment and History** separate the reading tasks. Completed normal-account orders show no preparation or messaging actions. Active orders expose one next-step button plus More actions. Selecting an action replaces the body of the same dialog with one focused workflow and a Back control; it does not stack another order/invoice modal.

Active operational warnings remain immediately visible. Terminal-order review text is retained under History as a recorded operational note rather than shown as a current preparation instruction. No historical note or canonical business control was deleted.

Implementation is in [admin-order-details.tsx](../../apps/web/components/admin-order-details.tsx), integrated from [admin.tsx](../../apps/web/components/admin.tsx), with scoped styles in [admin-compact.css](../../apps/web/app/admin-compact.css). Existing additions, inspection, handover, invoice and consent components/APIs remain authoritative. Optional embedded/compact/history-only modes leave existing customer/driver defaults in place. `OperationForm` explicitly imports React so these newly exercised form renders can also be validated in the Node SSR harness.

The only backend change projects existing `users.provisional` as `customer_provisional` for already-authorised staff order reads. This supports relevant phone-account actions without guessing from names or exposing editable context IDs. Customer payloads omit the flag; original customer/driver/branch scoping and delivery-code filtering remain. No new mutation endpoint, schema migration or authorization relaxation. [Source preservation](evidence/control-preservation.json) confirms canonical delivery/addition/tracking/channel/activation/document controls and customer/driver page source unchanged.
