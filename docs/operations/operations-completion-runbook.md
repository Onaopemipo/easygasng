# Operations continuation — local review and safe rollout

5 November 2026. Production NO-GO remains. This is a partial implementation continuation, not completion of the consolidated brief. The Excel migration/import hold is unchanged. No real messages, provider charges, online payments, orders, stock adjustments or role changes were created by the tests.

## Local controls and customer journeys

- Orders: view a record, open **Visit changes and photo history**. Owner/manager/sales can record a provisional customer's specifically requested transactional and OTP channel permissions, then request a secure completion invitation after password re-verification. Staff cannot record marketing/refill opt-in on a customer's behalf. No customer phone code is shown to staff.
- Customer follows `/activate#<random-token>`, requests a code, verifies it before private order data is returned, and sets a password/accepts terms. The original identity and order remain. The fragment is removed from browser history. Expiry, revocation, resend limits, committed failed-attempt counts and replay checks apply. Returning customers can use activated-phone/password sign-in on web and native. Existing email sign-in is retained.
- Orders → invoice: immutable original snapshot remains. Finance/owner proposes a credit, debit or unpaid void with reason; a different finance/owner approves. Approved decisions and note events cannot be overwritten. Payment requests bind customer, invoice version, outstanding amount, currency and expiry. A pending correction suspends request review; an approved correction revokes old requests. Customer sign-in is required. These are hosted review/collection requests, not connected online checkout. No screenshot proves settlement.
- Corrected financial totals do not silently rewrite original order totals or authorise a different cash handover. Pending notes, voids and totals that do not reconcile with the fulfilment order block dispatch/handover. Full adjustment-to-fulfilment reconciliation remains engineering work.
- Deliveries: **Driver trips, vehicle and fuel records** registers approved suitable vehicles (owner, reauthenticated), records duty trips and start/end odometers, and records fuel purchases with references. **Area dispatch** lists real order areas/windows and explains driver recommendations. Server assignment checks branch, vehicle suitability, aggregate gas load, existing stock/cylinder/payment/driver/capacity controls. New enhanced assignments require acknowledgement before pickup. Pre-pickup reassignment preserves the previous attempt/evidence, rotates the delivery code, notifies drivers and revokes old-driver access. Picked-up goods cannot be reassigned without the established physical return/inspection controls.
- Driver visit: acknowledge/reject; propose extra gas; customer independently reviews the proposal. Additional same-visit delivery fee is zero in the proposal. **Commit remains disabled:** a price quote is not verified van stock, custody, additional-payment verification or a delta fulfilment invoice. Original order and stock remain unchanged.
- Proof: an assigned driver uploads consented JPEG/PNG/WebP evidence, with bounded decode/pixel/byte limits and WebP re-encoding that strips metadata. Each order retains separate historical evidence. Customer/admin reads are ownership/branch scoped and private/no-store. Latest eligible profile image is a derived pointer to an actual delivered attempt, not replacement of an older photo. Late offline upload requires a capture time within the same completed attempt. Capture time is a device-reported claim, not independently attested. Approved retention is required in production. The worker purges expired image bytes while immutable metadata/hash remain; expired reads are unavailable. Secure backup retention/vacuum practices also matter; no immediate erasure from historical backups is claimed. External malware scanning is not implemented or claimed.
- Native driver Orders: trip/fuel controls, assignment response, amendment proposals and order photo/invoice review are integrated into the existing driver navigation. Foreground GPS requires an active consented trip and platform permission; capture stops when leaving the screen/app or ending duty. No background mode is enabled. GPS/status/fuel/photo records use authenticated encryption with an account/device key in SecureStore and a bounded local file queue. Stable event/operation IDs survive retries; authenticated pending writes are recovered, corrupt files remain for review. Reconnection polling attempts sync; unresolved server conflicts retain the records. Offline GPS is not live tracking or a live ETA. Location recorded outside authorised duty is rejected. Do not end a trip while local records need reconciliation.
- Customers: **Retention and win-back follow-ups** uses actual delivery-completion timestamps and ledger-backed completed orders. Missing delivery history stays low-data. Staff can assign follow-ups and record immutable outcomes. Settings → Retention and win-back policy uses the existing shared independent approval workflow. Default is disabled; positive approved budget/cost ceiling and separate purpose/channel marketing consent are needed. One user contact/day and quiet hours are rechecked by the worker. Reservations against the monthly message budget are conservative estimates, not actual provider billing or conversion claims.
- Account settings: SMS/WhatsApp consent is purpose-specific; transactional consent does not authorise marketing. Turning it off cancels pending messages. STOP received through authenticated Meta callbacks suppresses WhatsApp marketing/refill messages. Termii inbound/receipt authenticity still needs provider-specific acceptance.

## Messaging configuration — no live activation in this task

Recommended for Nigeria: Termii SMS/OTP using its approved transactional/DND route and Meta official WhatsApp Business Platform. Recommendations do not create an account or approve a paid plan. Termii official API reference: https://developers.termii.com/messaging-api . WhatsApp official developer hub: https://whatsappbusiness.com/developers/developer-hub/ . Exact Meta template and authentication-template contracts need sandbox validation; a mocked acceptance is not proof of WhatsApp OTP delivery.

`APP_URL` is the canonical application origin. `.env.example` lists disabled flags and secret placeholders. A new random **local-only** `EASYGAS_MESSAGE_ENCRYPTION_KEY` was added to ignored `apps/web/.env.local` when absent. It is not a provider credential. Keep it confidential and retain it with recovery material: rotating it without a plan makes old encrypted outbox bodies/replay URLs unreadable. No actual key is in documentation or test output.

Before SMS: approved Termii account/base URL, API key, sender ID and transactional route; verify Nigeria network/DND delivery and receipts in the provider sandbox/approved test numbers. Before WhatsApp: approved business account/phone, explicit Graph version, secret token/app secret, approved templates and exact template parameters. Use signed Meta webhooks at `/api/messaging/meta`; verify challenge secret, raw-body HMAC, event deduplication and monotonic delivery states. Acceptance is labelled accepted, never delivered without a receipt. Unknown/ambiguous send outcomes are quarantined instead of blindly resent; explicit HTTP 429 rate limits back off and dead-letter after bounded attempts. There is no unapproved channel fallback. SMS receipt authenticity, automatic provider reconciliation and account-specific template acceptance remain open.

Run the existing supervised worker (`npm run worker -- --watch`) only under the documented database ownership rules; embedded PostgreSQL cannot be owned by the web server and a second process simultaneously. Disabled adapters do not send messages. Queue events/history remain visible. Worker scheduling/monitoring, operational escalation and provider billing reconciliation must be accepted before release.

Online payments remain unconnected. No payment gateway, webhook settlement, refunds or card collection is activated by these messaging settings.
