# Customer dashboard architecture

The existing catch-all app/[...slug]/page.tsx renders Site. Protected customer routes validate the existing cookie session server-side through auth.actor; unauthenticated requests redirect to the existing login with an internal return destination. No second identity provider, profile, cart or session store was introduced.

Site retains the shared public shopping context and existing business screens. CustomerWorkspace wraps all 15 configured routes for customer/commercial accounts, including public services/help when authenticated. Driver and technician administration/native experiences remain unchanged. CustomerDashboard renders the new overview and CustomerAccountMenu is shared with the public header. The official HD logo and existing cylinder illustration are reused. There is no customer hero CMS in this repository; no CMS was introduced.

customer-navigation.ts is the single route/group configuration and safe return/cart parser. Expanded sidebar is 276–280px, compact 76px, mobile drawer at <=900px; tablet defaults compact if no saved preference. Preferences are per-user, local, UI-only. Drawer background uses inert, Escape, focus restoration and a focus trap. Full final keyboard-cycle, tablet and assistive-technology verification are separately tracked, not assumed.

customer-data.ts provides independent abortable data requests, per-card skeleton/error/retry states, a 12-second timeout, coalesced mutation/focus refresh and cleanup. Navigation indicators poll at 30 seconds while visible. Source failures clear their own data. Widgets also have a render error boundary. No new subscription/worker or runtime dependency was added.

The customer.dashboard read model accepts only a strict widget enum (navigation/orders/activity/history), permits customer/commercial actors and binds actor.id to every private query. Orders aggregate actual statuses; activity combines owned source events with stable IDs/timestamps and existing destinations; history includes only verified paid, delivered gas purchases with payment evidence and delivery provenance. It does not claim measured consumption. Wallet and reward summaries use existing signed ledgers; schedules and prediction profiles reuse their existing APIs. Refill profile responses now expose the owned verified history and typical interval derived from the unchanged forecast. No pricing, approval, stock, accounting or forecast arithmetic was changed. Additive migration032 admits already_refilled/remind_later feedback states. The existing worker and profile read model share refill-feedback.ts: self-reports suppress stale predictions until a later verified refill; snooze suppresses estimated reminders for 24 hours. Existing notifications for that profile are marked read when superseded, without deleting history. No new purchase is fabricated.

See the complete RTM, route matrix, security notes and executed test evidence. Remaining requirements are explicit in the coverage report. Public commercial release remains NO-GO.
